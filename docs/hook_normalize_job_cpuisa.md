# `hook_normalize_job_cpuisa`

## Overview

`hook_normalize_job_cpuisa` is a queue-time OpenPBS hook that normalizes `cpu_isa` requests in every chunk of `Resource_List.select`.

A user can request one CPU ISA token, a comma-separated list of tokens, or use `compat[XX]` to request the explicitly named ISA `XX` together with CPU ISA values configured as binary-compatible alternatives. The hook converts this syntax into the ordinary comma-separated value used by the `cpu_isa` `string_array` resource.

Ordinary user-provided tokens are preserved exactly. Only `compat[...]` has special meaning. Hook-generated compatibility alternatives can optionally be filtered against the aggregate cluster `cpu_isa` inventory, while the ISA explicitly named by the user is always retained.

The hook shares its JSON configuration with `hook_discovery_cpus`.

## User documentation

### Exact CPU ISA requests

A normal token is used exactly as supplied:

```bash
#PBS -l select=1:ncpus=8:cpu_isa=x86-64-v2
```

remains:

```text
cpu_isa=x86-64-v2
```

The same applies to ARM ISA names:

```bash
#PBS -l select=1:ncpus=8:cpu_isa=armv9-a
```

Several acceptable ISA values can be supplied as a comma-separated list:

```bash
#PBS -l select=1:ncpus=8:cpu_isa=x86-64-v2,x86-64-v3
```

The hook removes duplicates and sorts the resulting list, but does not otherwise reinterpret ordinary tokens.

### Compatibility requests

`compat[XX]` requests `XX` itself plus the compatibility alternatives configured for `XX`.

For example, with the supplied x86-64 configuration:

```text
cpu_isa=compat[x86-64-v2]
```

is expanded to:

```text
cpu_isa=x86-64-v2,x86-64-v3,x86-64-v4
```

Likewise, an ARM compatibility entry is taken from the `aarch64` compatibility map. For example, according to the supplied configuration:

```text
cpu_isa=compat[armv9-a]
```

expands to:

```text
cpu_isa=armv9-a,armv9.1-a,armv9.2-a
```

A `cpu_isa` value may mix ordinary and compatibility tokens:

```text
cpu_isa=x86-64-v1,compat[x86-64-v3]
```

The final result is the union of all explicitly requested values and all generated compatible values, sorted with duplicates removed.

### Architecture selection

Compatibility maps are grouped by `cpu_arch`, such as `x86_64` and `aarch64`.

Normally the hook can determine the correct architecture map because the requested ISA token occurs in exactly one configured map. Therefore this is sufficient:

```text
cpu_isa=compat[x86-64-v2]
```

If a select chunk explicitly contains a single `cpu_arch`, that architecture map is used for compatibility lookup:

```text
cpu_arch=aarch64:cpu_isa=compat[armv9-a]
```

If the same ISA key were configured in more than one architecture map and the chunk did not identify one architecture, the request would be rejected as ambiguous.

If `compat[XX]` names a token that is not a key in the applicable compatibility map, the hook keeps `XX` and adds no alternatives. Unknown ordinary tokens are likewise retained; normal scheduler matching determines whether such a request can run.

### Cluster inventory filtering

When the shared configuration contains `state_file` and that file exists and contains an aggregate `resources.cpu_isa` inventory, only hook-generated compatibility alternatives present in that inventory are kept.

For example, suppose configuration defines:

```text
compat[x86-64-v2]
    -> x86-64-v2,x86-64-v3,x86-64-v4
```

but the aggregate cluster inventory contains only:

```text
x86-64-v2,x86-64-v3
```

The normalized request becomes:

```text
cpu_isa=x86-64-v2,x86-64-v3
```

The explicitly requested `x86-64-v2` is never removed by inventory filtering. Only alternatives generated by the hook are filtered.

If `state_file` is absent from the configuration, the file does not exist, or its inventory cannot be used, compatibility expansion still proceeds from the static configuration without inventory filtering.

### Multiple select chunks

Every chunk containing `cpu_isa` is normalized independently. Chunks without `cpu_isa` are unchanged.

For example:

```text
1:ncpus=8:cpu_isa=compat[x86-64-v2]+2:ncpus=16+1:ncpus=4:cpu_isa=armv9-a
```

normalizes the first and third chunks independently and leaves the middle chunk untouched.

## Technical and administration documentation

### Hook event

The supplied `hook_normalize_job_cpuisa.qmgr` installs the hook for the `queuejob` event with order 10. The Python implementation also recognizes `modifyjob`, so administrators can add that event if CPU ISA requests should also be normalized when jobs are modified.

The hook does not perform CPU discovery. `cpu_arch` and the vnode's exact `cpu_isa` are published by `hook_discovery_cpus`.

### Accepted `cpu_isa` syntax

An ordinary token must match:

```text
[A-Za-z0-9][A-Za-z0-9_.-]*
```

A compatibility token has the form:

```text
compat[TOKEN]
```

A complete resource value is a comma-separated list of these items. Empty items, nested wrappers, empty `compat[]`, and other expression syntax are rejected.

Examples of valid values include:

```text
x86-64-v3
armv9-a
x86-64-v2,x86-64-v3
compat[x86-64-v2]
compat[armv9-a],armv8.9-a
```

### Normalization algorithm

For each `select` chunk containing `cpu_isa`, the hook:

1. parses the comma-separated value;
2. keeps every ordinary user token unchanged;
3. replaces each `compat[XX]` expression with the explicit user value `XX` plus the configured compatible alternatives for `XX`;
4. determines the applicable CPU architecture from a single explicit `cpu_arch` in the chunk when available, otherwise from the unique compatibility map containing `XX`;
5. optionally filters only generated alternatives against the aggregate `resources.cpu_isa` inventory;
6. combines all explicit and generated values;
7. removes duplicates, sorts the values, and writes the normalized comma-separated list back to the chunk.

The explicit `XX` from `compat[XX]` is considered a user-provided value. Even if the compatibility list itself also contains `XX`, that value is not treated as a generated alternative and is never removed by inventory filtering.

### Shared configuration

The hook imports the same JSON configuration source as `hook_discovery_cpus`. The relevant fields are:

| Field | Description |
| --- | --- |
| `cpu_isa` | Architecture-keyed compatibility maps. Each ISA key maps to the complete list of vnode ISA tokens that can satisfy a compatibility request for that ISA. |
| `state_file` | Optional aggregate cluster inventory. A relative path is resolved below `PBS_HOME`. |
| `backup_user_select` | Optional boolean controlling backup of the pre-normalized `select`; defaults to `true` if omitted. |

The supplied shared configuration contains structures such as:

```json
{
    "cpu_isa": {
        "x86_64": {
            "x86-64-v2": [
                "x86-64-v2",
                "x86-64-v3",
                "x86-64-v4"
            ]
        },
        "aarch64": {
            "armv9-a": [
                "armv9-a",
                "armv9.1-a",
                "armv9.2-a"
            ]
        }
    }
}
```

The order of items in a compatibility list is not significant to this hook because the final resource value is sorted. Compatibility semantics are therefore completely explicit in the configuration rather than inferred from lexical or version ordering.

### Aggregate state file

When configured, `state_file` is expected to contain an object of the form:

```json
{
    "resources": {
        "cpu_isa": [
            "x86-64-v2",
            "x86-64-v3",
            "armv9-a"
        ]
    }
}
```

A relative `state_file` path is resolved below `PBS_HOME`. `PBS_HOME` is taken from the environment, then from `PBS_CONF_FILE`, with `/var/spool/pbs` as the fallback.

Missing or unusable aggregate state does not reject a job. The hook logs the condition and skips inventory filtering.

### Preserving the original select

By default, immediately before this hook first changes `Resource_List.select`, it stores the current select in `Resource_List.user_select` if `user_select` is unset or empty. If another earlier normalization hook already populated `user_select`, its value is preserved.

This behavior can be disabled by adding:

```json
"backup_user_select": false
```

to the shared configuration.

`user_select` is a metadata resource defined by the common select-normalization setup. It should not be included in the scheduler's `resources` list.

### PBS resources

This hook creates no PBS resources. Its Qmgr setup assumes the following existing resources:

| Resource | Type | Flags | Purpose |
| --- | --- | --- | --- |
| `cpu_arch` | `string_array` | `ho` | CPU architecture published by CPU discovery and optionally requested in a job chunk. |
| `cpu_isa` | `string_array` | `ho` | Exact vnode ISA token and normalized job ISA alternatives. |
| `user_select` | `string` | none | Optional backup of the original select expression; defined by the common normalization setup. |

`cpu_arch` and `cpu_isa` are defined by `hook_discovery_cpus.qmgr`.

### Qmgr installation

The supplied setup imports:

```text
/root/openpbs.hooks/hooks/hook_normalize_job_cpuisa.py
```

and shares the CPU discovery configuration source:

```text
/root/openpbs.hooks/config/hook_discovery_cpus.json
```

No resources are created by `hook_normalize_job_cpuisa.qmgr`, avoiding duplicate resource definitions when the CPU discovery and normalization hooks are installed together.

### Failure behavior

Malformed user `cpu_isa` syntax and ambiguous configured architecture lookup reject the submission with an `invalid cpu_isa specification` message.

Unknown ISA tokens are not themselves errors. They remain in the normalized request and normal scheduler matching determines whether a suitable vnode exists.

Unexpected hook failures are logged with a traceback and reject the event rather than accepting a partially normalized request.
